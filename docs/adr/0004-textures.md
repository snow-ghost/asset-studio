# ADR-0004: Текстуры — рецепт в метаданных, пиксели в GLB, одна дверь для файлов

**Статус:** Accepted · **Дата:** 2026-09-12 · **Спека:** 002

## Контекст

M2 вводит текстуру как самостоятельный ассет (PNG с диска или процедурный из параметров) и как часть
модели (слот базового цвета материала). Три вопроса нельзя было решить «как получится»: где хранить
рецепт процедурной текстуры, чтобы открытая текстура снова редактировалась; что считать сохранённой
текстурой внутри модели, если экспортёр перекодирует изображение; и как принимать файлы двух форматов
через один вход, не размножая проверки.

## Решение

**Рецепт — в метаданных ассета, не в PNG.** Поле `procedural` в `<id>.json`; сервер хранит его как
непрозрачный JSON-объект до 4 КиБ и разрешает только у вида `texture`; схема — у фронтенда
(`domain/texture.ts`). Причина, названная на ревью: дизайнер может открыть PNG во внешнем редакторе и
пересохранить — `tEXt`-чанк пропадёт вместе с параметрами, а `<id>.json` останется нетронутым. Ассет
по-прежнему два файла (ADR-0002), в манифест поле не попадает (инвариант 7). Открытая текстура показывает
пиксели файла — это то, что видит игра; правка любого параметра перегенерирует её из рецепта.

**Что не тронуто, не переписывается.** Импортированный PNG сохраняется байт-в-байт; открытый ассет без
правки пикселей при Save уходит без нагрузки (обновляются только метаданные); рецепт с изменёнными
параметрами рендерится заново. Так пересохранение не превращает файл в другой файл без причины.

**Текстура в модели — пиксели, не байты.** `GLTFExporter` перекодирует изображения через canvas, поэтому
байты PNG внутри GLB не совпадают с исходником. Критерий round-trip сравнивает декодированные пиксели и
размер. Чтобы пиксели совпали без переворотов, текстуры для материалов создаются в ориентации glTF
(`flipY = false`, sRGB): экспортёр записывает их как есть, загрузчик читает как есть. Предпросмотр
текстуры-ассета на плоскости — отдельный объект и может быть ориентирован «как в графическом редакторе».

**Одна дверь для файлов.** `domain/import.ts::inspectImport` различает PNG и glTF по байтам, потом
спрашивает, подходит ли выбранный вид: PNG под видом модели — «выберите вид texture», glTF под `texture`
— «модели импортируются как glTF», иначе — «не glTF и не PNG». Порядок важен для сообщения дизайнеру.
На сервере зеркальное правило: `FormatsFor(kind)` таблицей и `ValidatePayload(format, bytes)` по
сигнатуре — то, что фронтенд проверяет до отправки, сервер проверяет до записи.

**Связь «модель ← текстурный ассет» не хранится.** Назначенная текстура встраивается в GLB; какой ассет
был источником, студия помнит только в текущей сессии (для панели). Автообновление модели при правке
текстуры — отдельная спека, если окажется нужным.

## Последствия

Процедурная текстура остаётся редактируемой после любого числа сохранений, а внешняя правка PNG её не
ломает — только заменяет пиксели до следующей правки параметра. Модель для игры — один файл. Цена:
пиксели текстуры в модели проверяются по содержимому, а не по байтам; текстура, назначенная из ассета,
после перезагрузки показывается как «embedded» без имени источника.

## Отклонённые альтернативы

- **`tEXt`-чанк внутри PNG.** Один файл вместо двух полей, но теряется при пересохранении PNG снаружи —
  ровно тот случай, ради которого рецепт и хранится.
- **Третий файл `<id>.params.json`.** Ломает «ассет = метаданные + нагрузка» ради поля, которому есть
  место в метаданных.
- **Внешние `uri` изображений в glTF.** Игра грузит два файла; манифест указывает на один. ADR-0002.
- **Сравнивать байты PNG в GLB.** Пришлось бы подменять изображения экспортёра исходными байтами —
  собственный экспортёр ради теста; пиксели доказывают то же самое.
- **Хранить ссылку на ассет-источник в метаданных модели.** Полезно для автообновления, но это функция,
  которой ещё никто не просил; поле «на всякий случай» противоречит инварианту 7 по духу.
